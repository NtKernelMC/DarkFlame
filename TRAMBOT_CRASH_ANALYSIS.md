# Подтверждённый дефект Lua: дамп 06.09.2026 в 08:49:58

Исследован `DarkFlameClientCrash_20260906_084958_186_P000057B0_T00004874.dmp`
(1 568 969 556 байт), созданный диагностической сборкой 08:43:16. Дамп, логи
и соответствующие DLL/PDB сохранены в `.codex-temp-dia2dump/tram-crash-084958`.
Отдельное зависание 08:46:11 закончилось закрытием игры: Windows записала
Application Hang 1002 в 08:46:39. Стека того зависания нет.

Свежий вылет — чтение `0x55` при обходе массива таблицы сборщиком мусора
(`client+278591`, соответствие `traversetable` подтверждено инструкциями).
Массив таблицы `685F76B8` указывает на память, уже не содержащую Lua TValue.
Главное Lua-состояние `504C9978` принадлежит `province_pilot`; это подтверждает
сохранённый `g_sessions` с символами точной DLL/PDB. Трамвай в этот момент ехал
после первой остановки, скорость по последней телеметрии — 0.2044.

## Причина

Встроенный Lua использовал собственный статический `dummynode_` для всех пустых
таблиц. Клиентская копия Lua сравнивает этот узел с адресом своего sentinel.
Для чужого адреса проверка не срабатывает: запись в пустую таблицу изменяет
общую константу встроенной копии, а освобождение может принять её за выделенную
память. В этой сборке страница DLL доступна для записи, поэтому порча не обязана
немедленно приводить к исключению.

В дампе `DarkFlameClient!dummynode_` по адресу `1017DD28` содержит ключ `1`
(Lua number) и значение `50E53CC8` (Lua function), хотя должен состоять из nil.
Функция принадлежит GC-списку трамвайного состояния. Пять таблиц из отдельного
GC-списка пилота содержат ту же чужую функцию в первом элементе массива,
включая его приватные globals `5A71B8F0`. Upvalue этой функции ведёт к globals
трамбота. Так сборщик одного состояния получает объекты другого, чьи GC-метки
и время жизни управляются независимо. Это конкретное нарушение владения;
саму последовательность предыдущих освобождений снимок не записывает.

Повреждённая таблица `685F76B8` всё ещё достижима через массив `50E52800`
и захваченную переменную трамбота, но уже отсутствует в обоих GC-списках.
Отправки PostMessage в стеке исключения нет. Этот дефект согласуется и с
предыдущими случаями испорченных Closure/UpVal; тождество причин всех зависаний
без стеков пока не доказано.

## Исправление и проверка

`Client/third_party/mta_lua/ltable.c` теперь создаёт собственный выделенный
hash-узел даже для пустой таблицы. Статический sentinel встроенного Lua больше
не передаётся клиентскому runtime. Обратный путь распознаёт пустой sentinel
хоста по состоянию таблицы и nil-узлу, включая сдвиг `lastfree` после неудачного
поиска свободного места. Такой узел не изменяется и не освобождается. Начальная
инициализация освобождает Table при ошибке выделения Node до включения в GC.

`Tests/run_lua_table_interop_test.cmd` собирает две независимые копии Lua:
host DLL с исходным `ltable.c` из коммита `931f97f` и текущий runtime. Проверены
300 циклов в каждом из двух состояний, запись/расширение таблиц в обоих
направлениях, выполнение сохранённых замыканий, GC обеими копиями, неизменность
sentinel хоста и пять точек отказа выделения. Учёт аллокатора не обнаружил
неправильных освобождений, несовпадений размера или утечек после закрытия VM.
Тест прошёл. Release x86 DLL собрана успешно.

Это исправление подтверждённого дефекта; для проверки поведения в игре нужен
полный перезапуск и повтор нескольких остановок. Постановка клавиш PostMessage,
ПКМ и алгоритмы движения этим исправлением не менялись.

Для зависаний подготовлен внешний сборщик `Tests/watch_game_hang.ps1`: после
подтверждения неотвечающего окна он сохраняет два полных снимка с интервалом
3 с и копии логов/DLL/PDB. На отдельном тестовом оконном процессе проверено
создание обоих дампов; процесс затем самостоятельно завершился с кодом 0.
Сборщик не завершает игру и запускается отдельно; сейчас наблюдение не активно.

Трамвай прошёл остановку 4428.70, завершил операции дверей и продолжил движение.
В 08:32:33.699 началось торможение к 4739.94, в 08:32:34.517 журнал подтверждает
`brake_reverse=true` и скорость 0.4230. Во время исключения дверной импульс
не выполнялся. PostMessage принимался игрой в этом запуске; это не доказывает
отсутствия других проблем ввода.

Исключение `C0000005` — исполнение по адресу `55CFDD50`. `!vprot` подтверждает
`MEM_PRIVATE / PAGE_READWRITE`, то есть это данные, а не исполняемый код.
Адрес возврата `client+275051`: непосредственно перед ним вызов указателя
C-функции Lua, загружаемого из Closure через текущий CallInfo. Соответствие
`luaD_precall` установлено по инструкциям и структурам, а не по ближайшему
экспортному имени plutovg: имена экспорта в этом стеке не являются символизацией.
Среди кадров до игрового цикла вызова dfEmulateKey нет.

Дамп частичный: отсутствуют CallInfo по адресу `3FD80C18`, часть прототипа,
строки констант и source. Сохранённый слот функции ссылается на объект, чьи
байты уже не соответствуют корректному Closure. Это свидетельство повреждения
состояния, но запись/освобождение, вызвавшие его, по этому снимку не установлены.
Разные значения указателя функции в регистрах исключения и позднее сохранённой
памяти также не позволяют восстановить историю только по дампу.

Сопоставлены основные поля стека, GC-списков, Closure и UpVal с инструкциями
клиентской VM. Это не полная проверка совместимости двух Lua runtime. Обнаружено
отдельное расхождение `nexpectedresults` (нативный код использует +08, встроенная
структура +84); его участие в краше не доказано. Изменения ABI/GC наугад не внесены.

Следующая сборка добавляет `MiniDumpWithPrivateReadWriteMemory`: сохраняются
приватные PAGE_READWRITE области, включая кучу Lua, а не только фрагменты,
достижимые из стеков. [Документация флага Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ne-minidumpapiset-minidump_type).
Дампы станут больше. Тест `Tests/run_crash_dump_memory_test.cmd` снимает снимок
отдельного собственного процесса без краша и проверяет фактическое сохранение
каждой страницы выделенного блока 1 МБ. Тест прошёл.

**Это улучшение диагностики, не подтверждённое исправление вылета.**
Для продолжения нужен игровой повтор с новой сборкой и новым дампом.

## Повторная проверка 06.09 в 08:09: трамвай не реагирует на ввод

В DarkFlame.log с 08:09:47 многократно записано W down: post=1, error=0,
scan=0x11, hwnd=0x000805E8. Это подтверждает постановку в очередь, не принятие
управления игрой. TramBot.log этого запуска пуст: его запись зависела от
выключенной настройки отладки в чате. Нового AppHang игры за этот запуск нет.

При сравнении с `300fdca` обнаружена регрессия: добавленный previous-state bit
на повторном down отличается от старой функции. В опубликованном обработчике
MTA `CKeyBinds::GetBindableFromMessage` такой down отбрасывается. Исправление
`PostMessage/reassert-v2` снова отправляет каждый явный down без этого бита.
Тест проверяет повторное нажатие после сброса состояния получателя с таким
фильтром. Это подтверждённая несовместимость, но игровой повтор ещё требуется.

TramBot.log теперь записывается и при выключенном чате отладки; добавлена
обратная связь игровых accelerate/brake_reverse и скорости. Также установлено,
что MTA ProcessMessage игнорирует сообщения Shift: прежний тест Win32 окна
не подтверждал Shift в игре. ЖБК по последнему указанию возвращён на
setPedControlState, только ПКМ раз в 2 с оставлена через dfEmulateKey.

## Что добавил дамп

Все 29 инструкций исполняемого Proto совпадают с компиляцией текущей функции
setDriveKey в TramBot.lua. Загрузочный префикс смещает строку на одну:
строка 497 в VM соответствует строке 496 файла. Вызов — setDriveKey("W", false, nil).
Сбой происходит при чтении keyState[key], до вызова api.emulateKey/dfEmulateKey.

Слот upvalue keyState указывает на объект с типом Lua table вместо UpVal,
а указатель значения нулевой. Тот же некорректный объект используется в
releaseKeys; соседний upvalue у releaseKeys корректен. Это подтверждает
повреждение состояния захваченной переменной и согласуется с повторным
использованием освобождённой памяти, но история освобождения/записи отсутствует.

Частичный дамп не содержит полного CallInfo и всех корней/соседних областей VM.
Источник порчи, а значит причинное исправление, пока не установлен. Замена одной
проверки, pcall или перенос callback не восстанавливают такое нативное состояние.
Доказанного обычного Lua-дефекта владения не найдено; TramBot не изменялся.
